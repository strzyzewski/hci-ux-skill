# Usability review: orders-mobile.html

Assumptions: users are end customers on touch phones (no hover); the order list shows only name and a colored dot; the address form is empty on load and applies to the account (not per order); the backend allows cancelling only some orders. Severity: 0 = not a problem, 4 = catastrophic.

| # | Principle | Location | Observation | Sev | Fix |
|---|-----------|----------|-------------|-----|-----|
| 1 | Accessibility of interaction / Fitts; Recognition over recall; Match with real world | `.row-actions` (l.17-18), `visibility:hidden` until `:hover` | Edit and Cancel are invisible on touch devices, where hover does not exist. Changing or cancelling an order is effectively undiscoverable or unreachable on phones, and keyboard/screen-reader users cannot reach them either (hidden elements are not focusable). | 4 | Always show the actions, or open a per-order detail screen with clear buttons. Never gate a primary action on hover. |
| 2 | Error prevention; User control and freedom; Visibility of system status | `cancelOrder()` l.85-88, trash button l.34/41/48 | One tap on a tiny trash icon irreversibly cancels (DELETE) with no confirmation, no undo, no feedback. The row is removed even if the request failed (response not checked), so the UI can show an order as cancelled when it is not. Also no check whether the order is already shipped. | 4 | Confirm with a specific dialog ("Cancel order #1042 Desk lamp?" with "Cancel order" / "Keep order"), check `res.ok` before removing, offer undo or a cancelled state, show refund/consequence info, and disable cancel for non-cancellable orders with an explanation. |
| 3 | Error recovery; Visibility of system status | submit handler catch block l.78-81 | On failure the form is reset, so the user loses everything they typed, and the message is a raw technical "Error: HTTP 500". No recovery guidance. | 4 | Keep the input, show a plain-language message near the button and move focus to it ("We couldn't save your address. Check your connection and try again."), and offer retry. |
| 4 | Visibility of system status; Accessibility (color not sole cue) | Status dots l.13-16, l.31/38/45 | Order status is conveyed only by a 10px colored dot with no text. Users cannot tell what green, yellow, red mean; color-blind users cannot distinguish them (red/green); screen readers get nothing. The main task "check order status" is not supported. Also "failed" red on an order gives no next step. | 4 | Show a text status label ("Shipped", "Delayed", "Payment failed") next to or instead of the dot, plus delivery estimate and a next step. Keep the color as a secondary cue with an icon. |
| 5 | Fitts's law / touch target size; Error prevention | `.icon-btn` 20x20px, gap 4px (l.19, l.17) | Targets are 20px, far below the 44-48px recommended minimum; the destructive trash sits 4px from Edit, so mis-taps cause accidental cancellation. | 3 | Min 44x44px targets, 8px+ spacing, and separate or visually distinguish the destructive action. |
| 6 | Match with real world; Accessibility; Recognition over recall | Icon buttons ✎ / 🗑 l.33-34 etc. | Icon-only buttons with a `title` tooltip (not shown on touch) and no `aria-label`. "Edit" is ambiguous: it navigates to a generic order edit page, and it is unclear that it relates to the delivery address. The trash icon suggests "delete" rather than "cancel order". Glyph rendering varies by device. | 3 | Use text buttons ("Change address", "Cancel order") or icon+label, with aria-labels. |
| 7 | Consistency / Minimize user memory; Flexibility; Task match | Address section l.53-64 vs order list | The address form is detached from the orders: it is unclear whether it changes the address for one order, all open orders, or the account default. No indication of which order is affected, and no way to change an order's address from the order row. The form is empty, not prefilled with the current address, so the user cannot see what is saved. | 3 | Put "Change delivery address" in each order's detail, prefill with the current address, and state the scope ("applies to order #1042"). Disable when the order has already shipped, with an explanation. |
| 8 | Error prevention; Efficiency; Minimalist design | `confirm('Are you sure you want to save your address?')` l.73 | A non-destructive, easily reversible action is blocked by a generic native confirm dialog. It adds friction and trains users to click through (making the real destructive cancel confirmation useless). Meanwhile the destructive action (cancel) has none. Confirmation is inverted. | 3 | Remove the confirm on save; show a review/summary or inline success state instead. Reserve confirmation for cancellation. |
| 9 | Visibility of system status | `#msg` l.65, l.77 | Success/error text appears below the form, possibly off-screen on a phone after tapping Save, and is not announced to assistive tech (no `aria-live`). It is unstyled, so success and error look identical. No loading state or disabled button, so double submits are possible. | 3 | Place the message next to the button, style success vs error, use `role="status"`/`aria-live`, and disable the button with a progress label while saving. |
| 10 | Error prevention; Help users recognize errors | Address inputs l.55-62 | No `required`, no validation, no inline errors, and no input hints. Postcode has no `inputmode`/pattern; `autocomplete="street-address"` is used on a single "street and number" field (it expects the full multiline address, so autofill may populate wrongly; `address-line1` fits). | 2 | Add required fields, `inputmode="numeric"` where appropriate, `address-line1`, and validate inline with specific messages on blur/submit. |
| 11 | Accessibility; Aesthetic and minimalist design | Order rows l.30-50 | Rows are not links or buttons, so tapping an order shows nothing: no order details (items, date, delivery estimate, tracking). Status checking has no detail view. Heading levels: `h1` styled but `h2` default size, and font sizes (14px labels) are small for phones. | 2 | Make each row a tappable link to an order detail page with status timeline, tracking, and the actions. Use consistent type scale (>=16px body). |
| 12 | Flexibility/efficiency; Visibility of system status | `editOrder()` l.84 | Edit performs full page navigation to an unspecified page with no feedback, and the in-page state (unsaved address) is lost. | 1 | Use a dedicated, labelled flow and warn about unsaved changes, or open inline. |
| 13 | Help and documentation; Match with real world | Whole page | No empty state, no contact/help path, no cancellation policy, no hint about the cutoff for changes (e.g. cannot change after dispatch). Customers in trouble (failed/delayed order) have no way to get help. | 2 | Add a short help link/contact and policy text near the actions, and an empty state when no orders remain after cancelling. |

Total: 13 findings. Top priorities: 1, 2, 3, 4 (blockers on all three main tasks), then 5-9.
